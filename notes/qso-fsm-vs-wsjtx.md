# QSO FSM の遷移妥当性 — WSJT-X との突き合わせ

> 起票日: 2026-08-12 / 対象: `webft8` main `6870fab`（v0.9.1）
> 状態: **未着手**。何を参照とするかは下記「参照の取り方」

## なぜ重要か

`QsoManager` の状態遷移は、間違っても**画面上は正常に見える**。相手に返すメッセージが
1 手ずれても「送信している」ようには見えるし、状態表示も何かしら出る。気づくのは相手が
応答しなくなってからで、そのときには原因が自分側にあるとは分からない。

さらに直接的な副作用がある。`app.js` の `onStateChange` は
**`IDLE` への遷移を「QSO 成立」とみなしてログに書き込む**（`qso.dxCall` があれば
`qsoLog.add(...)` → トースト）。誤って `IDLE` に落ちれば、成立していない QSO が
ログに残る。取り消す手段は用意されていない。

## 現状の FSM

`ft8-web/www/qso.js` は `QSO_STATE` を **export している**（`IDLE` / `CALLING` /
`REPORT` / `FINAL`）。`QsoManager` も export 済みで、**node から素で駆動できる**
（`tests/unit/qso-report-format.test.mjs` が既に実証）。**スタブが一切要らない**ので、
本プロジェクトのテスト対象の中で最も着手コストが低い。

UI との連携も既に継ぎ目がある。`app.js` は `onStateChange` / `onTxReady` を
**注入**しているので（`app.js:600` 付近）、記録用コールバックを渡せば
「どの遷移でどの UI 通知が飛ぶか」まで単体で表明できる。DOM を触る
`updateQsoDisplay()` 側だけが `app.js` に残るため、そこは Phase 1 の抽出範囲と重なる。

## 参照の取り方

**WSJT-X の doc やコメントではなく、実装を読む**（`notes/` の他の記録と同じ方針）。
自動シーケンスの本体は `mainwindow.cpp` の Tx1〜Tx6 選択ロジック。突き合わせるのは
「ある状態で、ある受信メッセージが来たとき、次に送るのはどれか」の表である。

素案（要検証。この表自体を WSJT-X の実装で裏取りしてから固定する）:

| 受信 | WSJT-X が次に送るもの | webft8 の現状 |
|---|---|---|
| `CQ DX` | Tx1 = `DX ME GRID` | 要確認 |
| `ME DX GRID` | Tx2 = `DX ME +RPT` | 要確認 |
| `ME DX +RPT` | Tx3 = `DX ME R+RPT` | `REPORT` へ |
| `ME DX R+RPT` | Tx4 = `DX ME RR73` | `FINAL` へ |
| `ME DX RRR` / `RR73` | Tx5 = `DX ME 73` | `FINAL` へ |
| `ME DX 73` | 終了（CQ へ） | `IDLE` へ → **ログ記録が走る** |

## 特に差が出そうな箇所

実装間で解釈が割れるのはここ。各項目を単独のテストにする。

- **グリッド省略**: 相手がグリッドを送らずいきなりレポートを寄越した場合
- **`RRR` と `RR73` の違い**: `RR73` は「了解＋73」の合成。`RRR` を受けた後の手が変わる
- **`73` を `REPORT` 状態で受けた場合**: 相手が手順を飛ばしている。追随するか無視するか
- **重複・遅延メッセージ**: 同じメッセージが次スロットにも来たとき、状態を進めてはいけない
- **自分宛でないメッセージ**: 他局の QSO に反応しないこと
- **こちらが送ったレポートと違うレポートが返ってきた場合**
- **リトライ上限**: `maxRetries` / `finalMaxRetries` の枯渇で `IDLE` に落ちるとき、
  **ログに書くべきか**。現状は `dxCall` があれば書く（`app.js` の `onStateChange`）。
  WSJT-X は交信不成立をログしない。ここは仕様判断が要る

最後の項目は既知の相違候補で、**未成立 QSO がログに残る**方向の誤りなので優先度が高い。
