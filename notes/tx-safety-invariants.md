# TX 安全性の不変条件 — 停止操作のあと何が成り立つべきか

> 制定日: 2026-08-12 / 対象: `webft8` main `57a8ed9`（v0.9.1）
> 契機: 「Stop Audio を押しても送信音が止まらない」（v0.9.1 で修正）

## なぜこの文書が要るのか

v0.9.1 で直した不具合は2つあり、性質が違った。

1. `AudioOutput.stop()` が `play()` の Promise を解決しない —— **実装のバグ**
2. `Stop Audio` に TX を止める処理が**最初から書かれていなかった** —— **要求の欠落**

2 の方が厄介である。存在しない機能は、ユニットテストでも CI でも原理的に検出できない。
テストは「書いた振る舞いが壊れていないこと」しか守れず、「書くべきだった振る舞いが無いこと」
は守れないからだ。

欠落を捕まえられるのは、実装から独立に「こうなっているべき」を先に書き下した表だけである。
この文書がその表であり、テストはここから導出される。**テストがこの表と食い違ったら、疑うのは
まず表ではなくテストと実装の方**にする。

## 停止経路

TX を止める入口は4つある。どれか1つでも下の不変条件を破ったら不具合とみなす。

| # | 経路 | 入口 |
|---|------|------|
| A | Stop Audio ボタン | `app.js` `toggleAudio()` の else 節 |
| B | Halt（■）ボタン | `app.js` `btnHalt` の click |
| C | オーディオデバイスの切断 | `app.js` `capture._onDisconnect` |
| D | WAV ドロップ時の自動停止 | `app.js` `handleFile()` |

**新しい停止経路を足すときは、この表に行を足してから実装する。** 逆順にすると v0.9.1 と同じ
抜け方をする。

## 不変条件

停止操作の完了後、以下がすべて成り立つこと。

| # | 条件 | 観測手段 | 破れたときに起きること |
|---|------|----------|----------------------|
| 1 | 出力デバイスに音が出ていない | 実測（VB-CABLE 経由の RMS） | 送信音が鳴り続ける |
| 2 | PTT off が実際に線に出ている | 実測（com0com 対向ポートのバイト列） | **送信機が送信し続ける** |
| 3 | `cat.pttOn === false` | 単体 | 次の `safePttOff()` が早期 return して PTT を落とせない |
| 4 | `periodMgr.hasTxQueued() === false` | 単体 | 停止したはずのスロットで送信が始まる |
| 5 | WSPR 保留タイマーが `null` | 単体 | 停止 1 秒後にビーコンが送信を始める |
| 6 | `txActive === false`、Halt ボタンが ↺ | 単体 | 送信中だと誤認され、Halt が復帰しない |
| 7 | 未解決の `play()` Promise が残らない | 単体（`tests/` で実装済み） | `await` が宙吊りになり 3 と 6 に伝播する |

### 重み付け

**2 が最も重い。** 音が止まらないのは聞けば分かるが、PTT が入りっぱなしは画面上何も起きて
いないように見えたまま送信機を焼く。1 が満たされていても 2 が破れていれば無音送信が続く。

### 3 について補足

`cat.safePttOff()` (`ft8-web/www/cat.js`) は `!this.pttOn` のとき早期 return する。つまり
`pttOn` はアプリが持つ PTT の唯一の記録であり、ここが実態とずれると**以後どの経路からも PTT を
落とせなくなる**。3 は 2 の前提条件である。

## 対になる開始側の条件

- Start Audio 単体では送信しない。送信は明示的に TX を仕込んだときだけ始まる
